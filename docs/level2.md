# 学習レベル2 ログインして地図を開く

レベル1で作った訪問拠点マップにログインを追加します。配布されたアカウントでログインし、ページを再読み込みしたときはサーバーにセッションを確認します。共有URLからアクセスした場合は、ログイン後に同じ拠点を表示します。

## 学習目標

- ログイン、セッション確認、ログアウトのHTTPリクエストを説明できる。
- Cookieをブラウザーに管理させ、ログイン状態に応じて表示を切り替える。
- ログイン前に開いたURLから、認証後に選択と検索条件を復元する。
- ログアウトやセッションの失効時に、取得済みの拠点データを画面とキャッシュから取り除く。

## 準備

1. [レベル1のSPA](level1.md)を用意し、レベル2の配布バックエンドを[共通の起動手順](README.md#バックエンドの起動)で起動します。ソースから起動する場合は、配布タグ `v2.0.0` のルートで `go run ./src` を実行します。レベル1のSQLiteを開くと、拠点データを引き継いで利用者とセッションのテーブルが追加されます。
2. 初期ログインIDは `student` です。講師がパスワードを指定する場合は、レベル2のデータベースを初めて開く前に環境変数 `TUTORIAL_INITIAL_PASSWORD` を設定します。未設定の場合は、ランダムに生成されたパスワードが初回の起動ログに一度表示されます。セッションの有効期間は8時間です。
3. レベル2のOpenAPI定義からクライアントを生成します。 [OpenAPI定義](../schema/level2/openapi.yaml) · [起動・生成手順](../examples/level2/README.md) · [OrvalとHey APIの技術比較](orval-hey-api-comparison.md#lv2-cookieセッション)

Viteの既定構成ではブラウザーで `http://127.0.0.1:5173` を開き、相対URLの `/api` と `/map` をプロキシ経由で利用します。バックエンドはログイン・ログアウト・拠点の書き込みで `Origin` を検証します。Viteのポートを変えた場合は、バックエンドを `-spa-origin http://127.0.0.1:5174` のように実際のオリジンを指定して起動します。HTTPSプロキシ経由で利用する場合は、`-secure-cookie` とブラウザーで開くHTTPSオリジンを指定します。

## Step 1 — Swagger UIでセッションの流れを確認する

[Swagger UI](http://127.0.0.1:8080/swagger/) に表示されるパスは `/session` と `/places` です。`servers` の `/api` が先頭に付いたURLへリクエストが送られます。

| 確認する操作 | リクエスト | 期待する結果 |
| --- | --- | --- |
| ログイン前に利用者を確認 | `GET /api/session` | `401` |
| ログイン | `POST /api/session` に `loginId` と `password` | `200`、利用者のJSON、`Set-Cookie` |
| セッションと拠点一覧を確認 | `GET /api/session` と `GET /api/places` | `200` |
| ログアウト | `DELETE /api/session` | `204`。本文は空で、Cookieを削除する `Set-Cookie` が返る |
| ログアウト後に拠点を取得 | `GET /api/places` | `401` |

開発者ツールのネットワーク欄で、ログイン応答の `Set-Cookie` と後続リクエストの `Cookie` を確認します。`tutorial_session` には `HttpOnly` と `SameSite=Lax` が設定されます。SPAは `GET /api/session` の応答で利用者を確認し、ブラウザーが対象リクエストにCookieを添付します。

## Step 2 — 起動時にログイン状態を確認する

1. SPAの起動時に `GET /api/session` を実行します。応答を待つ間は確認中と表示します。
2. `200` の場合は利用者情報と拠点画面を表示し、一覧と詳細の取得を始めます。`401` の場合はログインフォームを表示します。通信失敗の場合は確認できなかったことと、再試行する方法を示します。
3. ログインフォームでIDとパスワードを受け取り、`POST /api/session` に送ります。資格情報に対する `401` はログイン欄のエラーとして表示します。送信中は同じ操作を重ねて実行できないようにします。

**完了条件**　未ログインで開いた場合はログインフォームが出る。認証確認中に拠点APIは呼ばれず、通信失敗とログインが必要な状態を区別できる。

## Step 3 — ログイン後に共有URLの拠点を表示する

1. 未ログインで拠点の共有URLを開いた場合は、`place`、`q`、`category` をURLに残したままログインフォームを表示します。
2. ログインに成功したら拠点画面を開きます。レベル0で作った手順で、同じURLから選択IDと検索条件を読み取り、一覧と詳細を取得します。
3. `http://127.0.0.1:5173/?place=1&q=ベルリン` で試します。サンプルデータではログイン後にブランデンブルク門が選択されます。

**完了条件**　ログイン後に共有URLの条件と詳細が表示される。再読み込み後もセッションが有効なら、その拠点を開ける。

## Step 4 — ログアウトとセッション失効を扱う

1. ログアウト操作で `DELETE /api/session` を送ります。`204` を受け取ったら拠点画面を閉じ、利用者情報と取得済みの拠点一覧・詳細をキャッシュから取り除きます。処理中の拠点クエリがあれば取り消します。
2. ログイン中に拠点APIがセッション失効を示す `401` を返した場合も、表示とキャッシュをクリアしてログインへ戻します。ログインフォームに対する資格情報エラーは区別します。
3. 期限切れを待たずに確認するには、同じViteオリジンを2タブで開き、一方でログアウトします。もう一方で検索などのリクエストを発生させ、`401` の後にログイン画面へ戻ることを確認します。

**完了条件**　ログアウト後にピンと詳細が消え、同じ共有URLを開いてもログインが求められる。

## 最終確認

- [ ] Swagger UIと開発者ツールでCookieの設定・送信・削除を確認した。
- [ ] ログイン情報の誤り、未ログイン、セッション確認時の通信失敗を画面で区別できる。
- [ ] ログイン後と再読み込み後に、共有URLの拠点と検索条件を復元できる。
- [ ] ログアウトやセッションの失効後は、取得済みの拠点が表示されない。
